# Frontend stack compatibility notes

**Research date:** 2026-10-19  
**Project state:** Repository currently contains a Gradle/Spring Boot backend and no frontend package manifest or lockfile, so there are no pinned frontend versions to validate. Recommendations below use current official documentation and should be locked together when the frontend is scaffolded.

## Recommendations

- **Next.js / React:** Start with the App Router and `create-next-app` current recommended defaults, then retain the generated lockfile and exact dependency graph. Current Next documentation requires Node.js 20.9 or newer and uses React canary in App Router builds (declare `react` and `react-dom` anyway for tools and ecosystem compatibility). Pin Next, React, and React DOM together; do not independently override React without checking Next's documented compatibility. [Next installation](https://nextjs.org/docs/app/getting-started/installation), [Next React version handling](https://nextjs.org/docs)
- **Tailwind v4 / shadcn/ui:** This is a supported pairing: shadcn documents Tailwind v4 and React 19 support. Use its current Next install and CLI flow, generated `components.json`, and generated CSS/config instead of hand-porting v3 conventions. Tailwind v4's PostCSS integration is `@tailwindcss/postcss` plus `@import 'tailwindcss'`; it does not target Sass/Less/Stylus, and its baseline browser support is Chrome 111, Safari 16.4, Firefox 128. If older browsers are required, use Tailwind v3. [shadcn Next install](https://ui.shadcn.com/docs/installation/next), [shadcn Tailwind v4](https://ui.shadcn.com/docs/tailwind-v4), [Next Tailwind/CSS](https://nextjs.org/docs/app/getting-started/css), [Tailwind compatibility](https://tailwindcss.com/docs/compatibility)
- **TanStack Query:** It works with App Router, but is optional: Next recommends native Server Component fetching where that meets the need, and TanStack itself advises avoiding Query until a concrete client-cache use case exists. For interactive client dashboards, create one browser `QueryClient` reused across renders and a fresh server client per request; set a positive `staleTime` to avoid an immediate duplicate browser fetch after hydration. Keep server/client data ownership clear and use prefetch/dehydrate/hydrate when the initial dashboard data should be ready in SSR. [Next data fetching](https://nextjs.org/docs/app/getting-started/fetching-data), [TanStack advanced SSR](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr), [TanStack SSR](https://tanstack.com/query/latest/docs/framework/react/guides/ssr)
- **Axios:** Use it for browser-side API calls if interceptors, shared request config, or non-fetch features justify it. Create a configured Axios instance; pass TanStack Query's `AbortSignal` through to Axios (`signal`) so obsolete queries can cancel. For server-side Next data access, prefer native `fetch` unless Axios behavior is specifically needed: Next extends `fetch` with its own memoization/cache controls, which generic Axios calls do not automatically inherit. Never expose private API credentials in a browser Axios instance. [Axios instances](https://axios-http.com/docs/instance), [Axios cancellation](https://axios-http.com/docs/cancellation), [Next data fetching](https://nextjs.org/docs/app/getting-started/fetching-data)
- **Zustand:** Use it for client-owned UI state (filters, selected account, transient layout state), not as a duplicate server-data cache; use TanStack Query for remote data. In App Router, avoid module-global mutable stores: make a store factory and provide it from a Client Component so requests/users cannot share state. Server Components should not read or mutate the Zustand store. If using persistence/localStorage, account for delayed hydration to prevent server/client markup mismatches. [Zustand Next.js guide](https://zustand.docs.pmnd.rs/learn/guides/nextjs), [Zustand persistence](https://zustand.docs.pmnd.rs/reference/integrations/persisting-store-data)
- **Prettier + Airbnb ESLint:** Separate formatting from code-quality linting. Run Prettier independently and add `eslint-config-prettier` last in the ESLint config so its stylistic-conflict rules disable formatting rules; avoid `eslint-plugin-prettier` unless there is a specific need. Airbnb's official `eslint-config-airbnb` is still a legacy shareable config, and its published peer range is ESLint `^7.32.0 || ^8.2.0`; that does not satisfy ESLint 9. If Airbnb is a hard requirement, pin a compatible ESLint 8 toolchain and use legacy config, then verify peer dependencies against the selected Node/Next versions. For ESLint 9+ flat config, use Next's supported config and explicit rules or another maintained flat-config implementation; do not assume the official Airbnb package supports flat config. [Airbnb config README](https://github.com/airbnb/javascript/blob/master/packages/eslint-config-airbnb/README.md), [Airbnb package metadata](https://github.com/airbnb/javascript/blob/master/packages/eslint-config-airbnb/package.json), [Prettier ESLint integration](https://prettier.io/docs/install.html), [Next installation/lint scripts](https://nextjs.org/docs/app/getting-started/installation)

## Practical setup sequence

1. Scaffold Next App Router with TypeScript and generated ESLint/Tailwind defaults; verify the Node runtime meets Next's current minimum.
2. Add shadcn/ui through its CLI before manually changing Tailwind configuration. Keep the CLI's generated tokens and component conventions consistent.
3. Decide whether server-rendered data or browser-managed dashboard data is needed route by route. Prefer Server Components + `fetch` for server-owned initial reads; add TanStack Query for browser cache, refetch, mutation, or interactive refresh needs.
4. Add a typed Axios instance for client API requests only if useful. Connect its `signal` option to query cancellation.
5. Add Zustand only for shared client UI state, with a per-request store factory/provider compatible with SSR.
6. Resolve linting before implementation: the compatibility decision is either official Airbnb on ESLint 8 legacy configuration, or ESLint 9+ Next flat config with selected Airbnb-style rules. Add Prettier and `eslint-config-prettier` after that choice.

## Compatibility caveats

- The source repository has no frontend manifests yet, so this is a stack-level compatibility review rather than validation against exact package versions.
- Next and React canary coupling in App Router means the generated Next dependency set is a safer starting point than assembling latest tags individually.
- Tailwind v4 raises the minimum supported browser baseline; confirm this against the product's audience before selecting v4.
- Official Airbnb ESLint package metadata currently limits ESLint to versions 7/8. Treat ESLint 9+ with Airbnb as a migration/compatibility project, not a drop-in configuration.
- Avoid competing state/cache owners: TanStack Query for server data in browser clients, Zustand for client UI state, and Next Server Components for server-side reads.
